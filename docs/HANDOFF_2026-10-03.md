## F15: the observer user never reaches a mounted standby's password file

Found when E2E step 10 failed with `Observer wallet does not authenticate for: dgtest_s.world`
(ORA-01017) right after step 9. Reproduced on the 19.27 `dgtest` pair with a throwaway user,
apply caught up, real-time apply running:

| Statement on the primary | Standby password file |
|---|---|
| `CREATE USER x IDENTIFIED BY …; GRANT SYSDG TO x;` | Not touched (60 s in steady state; 15 min and a log switch for step 9's own user) |
| then `ALTER USER x IDENTIFIED BY "<same password>";` | Rewritten within 1 s; `x` listed with `SYSDG=TRUE` |
| `CREATE; GRANT SYSDG; GRANT CREATE SESSION; ALTER USER … IDENTIFIED BY` in one session | `x` on the standby within 1 s |
| `REVOKE SYSDG` / `DROP USER` | Propagated within 1 s |

Oracle's documentation says a grant of an administrative privilege is propagated; on this
pair it was not. My reading (not from Oracle): a mounted standby cannot read the dictionary,
so a grant alone gives it no verifiers to build the entry from, and the password change
carries them. Before F13 made the standby login mandatory, the observer silently had no login
on the standby.

The fix (this commit) re-sets the password after the grant in `primary/09_configure_fsfo.sh`,
`add_observer/01_prepare_primary.sh` and `observer_sys_to_sysdg/01_create_sysdg_user.sh`,
makes step 9 prove the observer's `AS SYSDG` login on the standby before it enables FSFO, and
corrects the messages and docs that promised automatic propagation. Details and the unit-test
results are in the fix plan under finding 15. **Lab verification is test plan row 12.12.**
