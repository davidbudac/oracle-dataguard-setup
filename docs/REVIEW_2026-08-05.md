# Oracle Data Guard Setup Scripts — Full Review (2026-08-05)

Five parallel review passes (primary workflow, standby/optional steps, status/diag tools,
triggers + handoff, common/infra + migration), findings verified against the source; items
marked **[live]** were additionally reproduced against the dbmint E2E VMs (`cdb1`/`cdb1_stby`).

Severity is by *user impact*: HIGH = silently wrong outcome or destructive/unrecoverable path;
MEDIUM = wrong-but-visible behavior, dead safety checks, or blocked legitimate use;
LOW = misleading output, exit-code contract breaks, polish.

---

## HIGH

### H1. Redo log size query picks an arbitrary log — undersized SRLs everywhere
`sql/queries/get_redo_log_size.sql` — `SELECT DISTINCT BYTES/1024/1024 FROM V$LOG WHERE ROWNUM=1`
(no `MAX`, no `ORDER BY`). With mixed-size ORLs (grown over time), step 1 can record the small
size; steps 2/4/5 then build undersized SRLs on both sides. Oracle refuses SRLs smaller than the
largest ORL → transport silently falls back to archiver mode; real-time apply / FASTSYNC /
MAXAVAILABILITY degrade with no error in steps 1–7. Fix: `MAX(BYTES)`, warn when `MIN <> MAX`.

### H2. FRA archive detection is unreachable
`primary/01_gather_primary_info.sh:337-353`. For an FRA-archiving primary, `V$ARCHIVE_DEST.DESTINATION`
returns the literal `USE_DB_RECOVERY_FILE_DEST` (non-empty), so the `if [[ -z ... ]]` block that is
the only place `USE_FRA_FOR_ARCHIVE=YES` can be set from `log_archive_dest_1` never runs. The literal
leaks into `primary_info_*.env` as a "path"; step 2 then offers it as the default standby archive dir,
and a default-accepting run has step 3 `mkdir -p USE_DB_RECOVERY_FILE_DEST` (relative dir!) and the
standby pfile gets `LOCATION=USE_DB_RECOVERY_FILE_DEST` → ORA-19905/ORA-16032. (Step 3 line 447 already
has a defensive guard against exactly this literal — confirming the leak.) Fix: treat the literal as
FRA=YES and clear `ARCHIVE_DEST_PATH` right after the query.

### H3. [live] Standalone handoff uses the TNS *alias* as the hostname in every connect string
`dg_handoff.sh:352-376`. `DGConnectIdentifier` is normally a TNS alias (`cdb1_stby.world`); because
it contains a dot it passes the "hostname-looking" regex and becomes `(HOST = cdb1_stby.world)` in every
TNS/JDBC descriptor handed to app teams. The `HostName = '...'` property in the same
`SHOW DATABASE VERBOSE` output is what should be used; the fallback grep (`"Host Name|HOST *="`)
doesn't match that spelling. Live run produced a fully unusable report (real hosts
`poug-dg1/2.localdomain`).

### H4. [live] Handoff verdict says HEALTHY while the configuration is broken
`dg_handoff.sh:644-663`, `primary/10_generate_handoff_report.sh:486-505`. Verdict logic looks only at
role, `V$ARCHIVE_GAP` (nearly always empty on a primary), and `dg_broker_start`. Live run: switchover
status `FAILED DESTINATION`, apply lag 350 sequences, broker `Configuration Status: ERROR` /
ORA-16625 — verdict printed **HEALTHY**, exit 0. `APPLY_LAG_SEQ`, `SWITCHOVER_STATUS`, and the
captured `$BROKER_OUTPUT` are never consulted.

### H5. Step 7 "verify" never inspects broker output — HEALTHY with no broker config
`standby/07_verify_dataguard.sh:249-267`. All four DGMGRL calls are `... 2>&1 || true`, printed and
discarded; `ERRORS`/`WARNINGS` untouched. Skip/fail step 6 and step 7 still prints
`OVERALL STATUS: HEALTHY` while `SHOW CONFIGURATION` printed ORA-16532 right above. Same for
wrong SYS password on `validate_network`. `dgmgrl_output_has_error()` exists in dg_functions and
is unused here.

### H6. Step 8 partial failure: SYS rotated to an unknown password AND propagation skipped
`primary/08_security_hardening.sh:204-223`. `ALTER USER ... IDENTIFIED BY` + `ACCOUNT LOCK` run in one
heredoc; if the second fails after the first succeeds (e.g. ORA-40365 on a pwfile format the line-148
guard didn't parse), the script clears `RANDOM_PWD` and `exit 1` — jumping over the standby
password-file propagation block and its ACTION REQUIRED banner. The primary's orapw was already
regenerated → standby copy stale → ORA-16191 at next transport reconnect, hours later, with an error
message that mentioned none of it. Fix: distinguish "nothing changed" from "password already rotated";
in the latter case still run propagation + print the action block.

### H7. [live-repro] Dedicated-user password mangled/executed by unquoted heredoc
`trigger/create_role_trigger_dedicated_user.sh:311-338`. `USER_PASSWORD` is interpolated into an
unquoted heredoc: `$`, backticks, and `\` are processed by bash first. `Secr$et#1` creates the user
with password `Secr#1` (script reports success; nobody can log in); a backtick is command-substituted
on the DB host. Fix: validate/reject shell-special characters at the prompt (as
09_configure_fsfo.sh already does for `"`), or pass via stdin.

### H8. NFS client script aborts on its own server's export — fstab never written
`nfs/02_mount_nfs_client.sh:70-81,187-194,251`. Script requires root; `01_setup_nfs_server.sh` exports
with root_squash and sets the share `oracle:oinstall 750`. Root is squashed to `nobody` → the `touch`
write test gets EACCES → exit 1 ("Check NFS export options and permissions") *before* the
`/etc/fstab` block, so the mount doesn't survive reboot. The same test also fails the already-mounted
fast path on re-runs. Even past that, the unguarded `chmod 750` (line 251) would abort under `set -e`.
Fix: run the write test as the share owner (`su - oracle -c ...`) and guard the chmod.

### H9. Migration verify step always fails on a successful migration; the decommission gate doesn't gate
`migrate_noncdb_to_pdb/05_verify_pdb_dataguard.sh:85-94,119-125` + `06_decommission_noncdb.sh:41-45`.
(a) The violation check greps `type='ERROR'` without `status<>'RESOLVED'` — the "requires
noncdb_to_pdb.sql" row stays type=ERROR/status=RESOLVED forever, so step 05 exits 1 on every good
migration (step 04 line 78 filters correctly, confirming intent).
(b) `record_state "verify_done" "true"` is written *before* the pass/fail decision, so step 06 —
REMOVE CONFIGURATION, SHUTDOWN, optional DROP DATABASE, `rm -rf` of staged datafiles — proceeds even
when verification failed. `verify_failures` is recorded but never read.
(c) The "standby" checks route through `dgmgrl -silent /` on the primary — DGMGRL `SQL` executes on the
connected DB, so "PDB present on the CDB standby" is asserted from the primary; and the applied-SCN
query references `V$ARCHIVED_LOG.APPLIED_SCN`, a non-existent column (ORA-00904 swallowed → `?`).
Nothing in step 05 proves the standby applied anything.

### H10. run_minimal.sh can execute noncdb_to_pdb.sql in CDB$ROOT
`migrate_noncdb_to_pdb/run_minimal.sh:36-64`. No `WHENEVER SQLERROR` anywhere, and sqlplus exits 0
after ORA- errors. If `CREATE PLUGGABLE DATABASE` fails, the next heredoc's `OPEN UPGRADE` and
`ALTER SESSION SET CONTAINER` both fail but execution continues — `@?/rdbms/admin/noncdb_to_pdb.sql`
then runs against the root container of a live CDB. Add `WHENEVER SQLERROR EXIT SQL.SQLCODE` to every
heredoc (the numbered scripts get it from `_lib.sh`).

### H11. dg_check_srl.sh: SRLs created without a THREAD clause are invisible to the per-thread count
`dg_check_srl.sh:134-142`. SRLs added without `THREAD n` (exactly what this repo's own step 4 /
`add_standby_logfile.sql` do) sit at `THREAD#=0` until first use, so the per-thread subquery counts 0 →
"ACTION REQUIRED" + DDL that would create duplicate SRLs on a compliant database, exit 1 — while
`dg_status.sh` (thread-agnostic count) says OK for the same DB. Count `THREAD# IN (t.thread#, 0)` or
count unassigned SRLs into a shared pool.

### H12. A completely down instance yields "WARNING", exit 1, from the triage tool
`common/dg_local_status_common.sh:308-326,448-465,725-...`. With the local instance down
(ORA-01034), every parsed field is empty; all assessments are gated on non-empty role vars so none
fire; DGMGRL's ORA-01034 doesn't match the broker-absent patterns → `ERRORS=0, WARNINGS=2`, exit 1.
The tool most likely to be run *because* the DB is down cannot say "down". Add an explicit
"local instance unreachable" error path when identity parsing yields no role.

### H13. [live] NFS client script self-mounts over the export on the server host, breaking every other client
`nfs/02_mount_nfs_client.sh` (found during live testing on 2026-08-06, after the original review).
The walkthrough runs the client script on both DB hosts, and the NFS server is usually one of them.
The export path and mount path are deliberately the same directory, so on the server host the script
NFS-mounted the share on top of its own export. `rpc.mountd` cannot re-export an NFS filesystem:
every subsequent client gets "Cannot export ..., possibly unsupported filesystem or fsid= required"
(client-side: `mount.nfs4: ... No such file or directory`), while the server host itself appears to
work. Fixed: the script now detects that the entered NFS server is the local host (hostname or any
local interface IP), skips the mount + fstab entry, verifies the local directory and write access
(as the share owner), and exits 0.

### H15. [live] Generated TNS aliases break on hosts with sqlnet `NAMES.DEFAULT_DOMAIN`
`primary/02_generate_standby_config.sh` (found during the 2026-08-06 E2E run). Alias
qualification keyed off the database's `DB_DOMAIN` parameter, but `NAMES.DEFAULT_DOMAIN` in the
client sqlnet.ora is independent: with the sqlnet domain set and `DB_DOMAIN` empty, the generated
unqualified entries (`dgnonc_s =`) are unreachable — resolution appends the domain and looks up
`dgnonc_s.world`. Steps 1–4 all pass (the entries grep fine); the failure surfaces mid-RMAN
DUPLICATE as `ORA-17627: ORA-12154` from the primary-side channel, landing the operator in
non-restartable step 5. The code's comment even claimed to handle this case. Fixed: step 2 now
reads `NAMES.DEFAULT_DOMAIN` from the primary's sqlnet.ora (TNS_ADMIN-aware) and qualifies both
aliases with it (a qualified alias resolves exactly under both sqlnet configurations); DB_DOMAIN
alone keeps the old behavior, and a DB_DOMAIN/sqlnet-domain mismatch warns.

### H16. [live] Step 4's thread-unassigned SRLs fail step 13's VALIDATE DATABASE preflight
`primary/04_prepare_primary_dg.sh` + `sql/commands/add_standby_logfile.sql` (found in the
2026-08-06 E2E run). SRLs created without a `THREAD` clause sit at `THREAD#=0`, and DGMGRL
`VALIDATE DATABASE` reports them as "standby redo logs not configured for thread 1" /
"Insufficient SRLs" — so step 13's preflight finds validation errors on a correctly-built
configuration and (per the M8 policy) aborts non-interactive runs. Same root cause H11 fixed in
`dg_check_srl.sh`, now fixed at the source: step 4 reads the instance's redo thread
(`V$INSTANCE.THREAD#`, default 1) and creates every SRL with an explicit `THREAD n` clause.
`dg_check_srl.sh`'s THREAD#=0 pool handling stays, for builds created before this fix.

### H17. [live] Step 4 never reloaded the listener — and the missing reload masked malformed listener.ora files
Follow-up to M14/M15, upgraded after the 2026-08-06 E2E run. Without a reload, the `_DGMGRL`
static registration stays inactive: steps 5–7 pass (nothing uses it yet) and the failure surfaces
in step 13's `VALIDATE DATABASE` StaticConnectIdentifier probe (ORA-12514) — or at the first real
switchover. Worse, never reloading means a syntactically broken listener.ora (see the husk bug
below) goes unnoticed until the next listener restart, i.e. a host reboot breaks the listener.
Fixed: step 4 now reloads the listener after changing listener.ora (approval-gated; `lsnrctl
reload` does not drop existing connections), waits, and verifies the `_DGMGRL` service is actually
registered; step 6's M15 check remains as a second gate. Related harness bug fixed in
`tests/e2e/drop_test_db.sh`: its cleanup deleted listener.ora lines matching the test SID, leaving
invalid `(SID_DESC = (ORACLE_HOME=...))` husks that made the next reload fail with TNS-01155 —
now it removes whole SID_DESC blocks (and husk blocks with no SID_NAME, self-healing old damage).

### H18. [live] Broker enabled DURING RMAN duplicate — stale broker files start apply mid-clone (ORA-01153)
`standby/05_clone_standby.sh` (found in the 2026-08-06 E2E run). The duplicate's `SPFILE SET`
list carried `DG_BROKER_START='TRUE'`, so DMON starts on the auxiliary in the middle of the
clone. If broker configuration files from a previous standby build exist (`dr1/dr2<unique>.dat` —
the documented re-clone reset procedure removes datafiles/redo but never broker files), the
standby DMON loads the old configuration, syncs with the primary's DMON, and starts managed
recovery while RMAN is still restoring → the duplicate dies with ORA-01153 at its final recovery
step. Fixed: the duplicate now runs with `DG_BROKER_START='FALSE'`; after the clone completes,
step 5 removes stale default-location broker config files for the standby and only then enables
the broker (before starting MRP). Related harness hazard fixed in `tests/e2e/drop_test_db.sh`:
its `rm -f dr1*.dat` glob would have deleted the broker files of *every* database sharing the
ORACLE_HOME (e.g. the persistent cdb1 pair on the test VMs) — now it removes only the test DB's
files by exact name.

### H14. [live] `dg_check_srl.sh` `clean()` did not strip tabs — every numeric field parsed as 0
Found by the Batch C implementation agent during live testing: sqlplus pads NUMBER columns with
tabs at large LINESIZE, the `*[!0-9]*` guards then rejected every value, and a fully compliant
database was reported "ACTION REQUIRED ... SIZE 0M" with bogus DDL, exit 1. Fixed together with M21
(tab-safe field handling + a separate `trim()` for text fields).

- **M13.** `primary/02_generate_standby_config.sh:377` — DB_UNIQUE_NAME collision check is

- **M14.** `primary/02_generate_standby_config.sh:335-345` — step 2 happily consumes a

- **M16.** `primary/01_gather_primary_info.sh:464,478,503` — the "never fails the step" redo-stats
