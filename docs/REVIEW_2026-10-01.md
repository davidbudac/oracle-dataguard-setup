# Oracle Data Guard Setup Scripts — Implementation Review (2026-10-01)

Scope: all 48 shipped shell scripts (~30k lines, `tests/**` excluded), the `sql/` snippets they
drive, and the docs that describe them (CLAUDE.md, README.md, `docs/*.md`, toolkit READMEs).
Architecture was deliberately **not** reviewed. That covers the NFS share, broker-first design,
the single `.env`, duplicated helpers in the standalone toolkits, and Linux-only `nfs/`. The
review covers implementation details only, with AIX 7.2 as a hard target.

Method:
- Eleven parallel review passes ran: steps 1-2, steps 3-5, steps 6/7/9/10/13, `common/`,
  status/triage tools, observer toolkits, `trigger/`, `dg_handoff.sh`, sync-impact + SRL check,
  migration + SYS→SYSDG toolkits, and a cross-cutting grep sweep.
- Every HIGH finding, and most MEDIUM ones, was re-read against the source.
- Findings marked **[repro]** were reproduced by running the extracted code locally.
- Nothing was run against a database or an AIX host. AIX behaviour is inferred from code reading,
  and findings that depend on uncertain platform behaviour say so.

Severity uses the same scale as `REVIEW_2026-08-05.md`:
- **HIGH**: a silently wrong outcome, or a destructive or unrecoverable path.
- **MEDIUM**: wrong but visible behaviour, a dead safety check, or blocked legitimate use.
- **LOW**: misleading output, a break in the exit-code contract, or polish.

## Summary

The AIX hygiene of the shipped code is good, and the cross-cutting sweep confirmed it:
- No `sed -i/-E`, `grep -o/-P/-A`, `date -d`, `/proc`, `stat`, `readlink`, `hostname -s`, fractional
  `sleep`, or bash-4 syntax was found outside guarded or printed-example contexts.
- `df -Pk`, `ps -p PID -o args=`, `tnsping` instead of `nc`, and the `wc | tr -d` trimming are all in place.
- The text that `dg_status.sh` sends over ssh is ksh-safe.
- All 13 DB-free unit suites pass.

The problems that remain fall into three groups:

1. **Fixes applied to only some copies of the same pattern.** `SET DEFINE OFF` before passwords,
   honouring `TNS_ADMIN`, per-alias tnsnames appends, the `CON_ID` filter, `umask 077` on the
   orapw copy, tab-safe `clean()`, and anchored broker-error regexes each exist in one place and
   are missing in their siblings. Section C lists every site.
2. **Paths that report success without having succeeded.** Examples are step 9's observer user, step 9's
   FSFO enable, step 10's exit-code mapping, step 7's broker check, the migration's step 05
   verification, the local engine's `IN SYNC` fallback, and `-n/--check` being announced and then
   ignored.
3. **Real AIX breaks.** These are the `boot` cron lines (`@reboot`, `*/5`), the backslash handling
   that `json_escape` relies on in awk, the untimed `/dev/tcp` probe, the `host` output parsing,
   and `_verify.sh` name resolution.

## HIGH

### H1. Step 9 reports the observer user as created even when the SQL failed
`primary/09_configure_fsfo.sh:318-324, 345-358, 387-402`. The CREATE USER and ALTER USER
heredocs have no `WHENEVER SQLERROR EXIT`, so `SELECT 'SUCCESS' FROM DUAL` runs after any error
and the `grep -q SUCCESS` check always passes. The following failures are all logged as "created
successfully", and the script goes on to enable FSFO with an observer that cannot log in:
- ORA-65096 (bad common-user name)
- ORA-28003 (password verify function)
- ORA-01920 (user already exists)
- a failed `GRANT SYSDG`

The existing-user branch (318-324) runs `GRANT SYSDG` without checking output at all.
Fix: add `WHENEVER SQLERROR EXIT SQL.SQLCODE` plus `SET DEFINE OFF` and check sqlplus's rc. Make
the existing `V$PWFILE_USERS` SYSDG check the authoritative post-condition.

### H2. `add_observer/01_prepare_primary.sh` exits silently when broker output is incomplete
`add_observer/01_prepare_primary.sh:188-192, 276-278`, `add_observer/_lib.sh:129-133`. The
script runs `set -e` + `pipefail`. The assignment `PRIMARY_HOST=$(broker_property ...)` ends a
`grep | head | sed` pipeline, so a missing `HostName`, `DGConnectIdentifier` or `LogXptMode` line
makes it return 1 and the script exits 1 with no message. That happens when dgmgrl fails, there
is no configuration yet, or the output format differs. `FLASHBACK_BLOCK=` behaves the same way
when VALIDATE produced no flashback block.

As a result, the `--primary-host`/`--standby-host` overrides and the "Re-run with --standby-host"
hint can never be reached, although `README.md:264` (troubleshooting) promises them. **[repro]**
Fix: end `broker_property` with `|| true`, or append `|| X=""` to each assignment.

### H3. `03_observer_ctl.sh boot` gives AIX users cron lines AIX cron rejects
`add_observer/03_observer_ctl.sh:357-368` (header `:15`), `add_observer/README.md:41,205-208`,
`01_prepare_primary.sh:675`. The output is labelled "Option B: cron (any platform, incl. AIX)"
and offers `@reboot ...` plus a `*/5 * * * *` watchdog. AIX cron supports neither `@reboot` nor
`*/N` step syntax, and no AIX alternative is printed.

The observer is therefore never restarted after a reboot on AIX, which is exactly the failure
`boot` exists to prevent. Fix:
- Add an AIX option using `mkitab "dgobs:2:once:/usr/bin/su - <user> -c '<env> <script> start' >/dev/console 2>&1"`
  or an `/etc/rc.d/rc2.d/S99dgobserver` script.
- Write the watchdog as `0,5,10,...,55 * * * *`.
- Remove the "incl. AIX" claim.
- Also export `LIBPATH` in the generated lines (see A7).

### H4. `dg_handoff.sh`: a failure in the HTML twin aborts the whole run with exit 2
`dg_handoff.sh:3137`. `render_handoff_html < "$OUTPUT_FILE" > "$HTML_FILE"` is unguarded under
`set -e`. If the awk converter fails (the project's own docs record AIX awk aborting with
`0602-558`), these never happen:
- the JSON sidecar
- `_tnsnames.ora`, `_jdbc.properties` and `_verify.sh`
- the stdout report
- the verdict exit code

The exit code is 2, which is also the "ERROR verdict" code, so step 10 and any monitoring
wrapper report a broken Data Guard. `dg_sync_impact.sh` already falls back for exactly this
case. **[repro]** (stub awk exiting 2). Fix:
`render_handoff_html <"$OUTPUT_FILE" >"$HTML_FILE" || { warn "HTML twin failed"; rm -f "$HTML_FILE"; }`.

### H5. Triage/diag wallet probe swaps the alias for a descriptor, so the wallet lookup probably misses
`common/dg_local_status_common.sh:266-310, 412`. `run_remote_sql_timeout` replaces
`/@<alias>` with `/@(DESCRIPTION=(CONNECT_TIMEOUT=5)...)`, the `tnsping`-resolved descriptor with
timeouts injected, before connecting. The secure external password store matches credentials on
the exact connect-string text, and `common/setup_dg_wallet.sh:420` stores them under the alias.
On any host where `tnsping` resolves the alias, which means every normal host, the wallet probe
would then always fail. `dg_triage_sid.sh` would fall back to "broker-only degraded mode" with
exit 1 on a healthy wallet.
**Confidence medium: confirm on dbmint.** If confirmed, keep the alias for wallet (`/@`)
connects and inject descriptor timeouts only on the password path, or bound the connect with
`SQLNET.OUTBOUND_CONNECT_TIMEOUT`.

### H6. Migration: `STANDBY_PDB_SOURCE_FILE_DIRECTORY` is set on the CDB primary only
`migrate_noncdb_to_pdb/04_plug_into_cdb.sh:57-60`, `run_minimal.sh:45-48`. `run_sql` uses local
OS authentication on the primary. The standby's recovery process reads this parameter, and
`ALTER SYSTEM` does not travel in redo. The standby therefore cannot find the staged files when
it applies `CREATE PLUGGABLE DATABASE`: apply stops, or the PDB's recovery is disabled on the
standby. This defeats the toolkit's "no manual copy on the standby" premise. Fix: set the
parameter on the standby instance (dgmgrl or sqlplus connected there) and verify it in step 05.

### H7. Migration: standby-side prerequisites are never created or checked
`01_preflight.sh:200-202`, `04_plug_into_cdb.sh:46-47`, `config.env.template:39-41`.
- The new PDB's datafile directory is created on the primary host only. `run_minimal.sh:24`
  does `ssh ... mkdir` on the standby, but scripts 01-06 do not.
- Nothing checks that `standby_file_management=AUTO` on the CDB standby, or that its
  `db_file_name_convert` covers `TARGET_PDB_DATAFILE_DIR`.
- The template's "the CDB standby uses the same path" contradicts this repo's own asymmetric
  layouts.

The result is ORA-01274, ORA-01119 or ORA-27040 on the standby after the plug-in. Fix:
preflight-check both parameters on the CDB standby. Create the directory there, or print the
exact command.

### H8. Migration step 05 can PASS while the PDB is not replicated, and it gates the destructive step 06
`05_verify_pdb_dataguard.sh:90-168`.
- The datafile check `grep -q '^STBY|'` accepts any row, including `UNNAMED000nn` placeholders.
- `V$PDBS.RECOVERY_STATUS` is never checked.
- A failed direct standby connection only logs a warning.
- `SCN_AFTER_PRI` and `APPLIED_SCN` are logged but never compared.

A standby that applies redo with the new PDB's recovery DISABLED (the 12.2+ behaviour when
plug-in files are missing) shows lag 0, the PDB row and datafile rows, so 05 writes
`verify_done=true`. Step 06 then lets the operator drop the only complete copy. Fix:
- Fail when the standby cannot be verified.
- Require `RECOVERY_STATUS='ENABLED'`.
- Reject UNNAMED names and compare datafile counts.
- Require `APPLIED_SCN >= SCN_BEFORE`.

### H9. Migration step 06 shuts down and drops whatever `SOURCE_ORACLE_SID` points at
`06_decommission_noncdb.sh:41-83`. No identity check is made before `SHUTDOWN IMMEDIATE` and the
optional `STARTUP MOUNT EXCLUSIVE RESTRICT; DROP DATABASE`:
- `v$database.name` is not compared with `SOURCE_DB_NAME`.
- Nothing checks that `cdb='NO'` and the open mode is READ ONLY.
- Nothing re-checks that the new PDB is OPEN READ WRITE in the CDB.

`01_preflight.sh` queries `NAME=` but never uses it. `verify_done` in `state.env` is never reset
by steps 01-04, so it can be stale from an earlier run, and `MIGRATE_NONINTERACTIVE=1`
auto-confirms. A mistyped SID drops the wrong database. Fix:
- Assert name, cdb and open_mode before any shutdown.
- Assert the PDB state in the CDB.
- Clear `verify_done` in step 01.

### H10. OMF mode: the standby inherits the primary's redo-log and file-name parameters — **FIXED**
Added after the initial review. The original passes missed it.

The step 5 OMF branch (`standby/05_clone_standby.sh`) runs `DUPLICATE ... SPFILE`, which copies
the primary's spfile to the standby and overrides only the parameters in its `SET` lines. It set
`DB_CREATE_FILE_DEST` and the FRA, and nothing else that controls file placement, so:
- **`DB_CREATE_ONLINE_LOG_DEST_1..5`** carried over from the primary. Under OMF rules they take
  priority over `DB_CREATE_FILE_DEST` for redo logs and control files, so the standby re-created
  its standby redo logs in the primary's directories. When those directories don't exist on the
  standby host, RMAN fails partway through (ORA-19504/ORA-27040), and step 5 can't simply be
  re-run. When they do exist, the redo logs silently land outside `db_create_file_dest`.
- **`LOG_FILE_NAME_CONVERT`/`DB_FILE_NAME_CONVERT`**, when present in the primary's spfile (for
  example a former standby), take priority over the OMF parameters in RMAN's naming order.

Nothing caught this earlier: step 1 never read these parameters, step 2 promised "everything
under db_create_file_dest", step 3 created only `db_create_file_dest` and the FRA, and E2E never
runs OMF mode.

Fix:
- Step 1 records the primary's online log destinations and whether the convert parameters are set.
- Step 2 (OMF mode) refuses when the convert parameters are set. It maps each
  `DB_CREATE_ONLINE_LOG_DEST_n` to a standby directory, defaulting to `db_create_file_dest` for
  n=1 and the FRA for n=2; the prompt only appears in interactive runs.
- Step 3 creates the mapped directories.
- Step 5 checks the live primary after the password is verified and before anything destructive
  happens. It `SET`s each destination explicitly in the duplicate and refuses to start RMAN on a
  convert parameter, a missing or unwritable directory, or a failed query.
- The shared helpers are in `common/dg_functions.sh`, covered by `tests/test_omf_online_log_dest.sh`.
- Not done: step 3's OMF disk-space check does not cover the extra directories.

## Cross-cutting themes (MEDIUM unless noted)

Each theme is one pattern that some copies already handle correctly. The fix is to carry the
existing correct version to the listed sites.

### C1. `&` in a password is substituted by SQL*Plus at most password sites
Only `common/dg_functions.sh:866-874`, `common/setup_dg_wallet.sh:210,233` and
`standby/05_clone_standby.sh:234` issue `SET DEFINE OFF` before embedding a password. These sites
send `CONNECT …"pw"` or `IDENTIFIED BY "…"` without it:
- `common/dg_local_status_common.sh:251-256, 318-323`
- `dg_check_srl.sh:109-115`
- `primary/09_configure_fsfo.sh:345-352, 387-395`
- `trigger/create_role_trigger_dedicated_user.sh:350-358`
- `add_observer/_lib.sh:88-97` (used by `01_prepare_primary.sh:382,402`)
- `observer_sys_to_sysdg/_lib.sh:75-83` (used by `01_create_sysdg_user.sh:158,181`)

With a password such as `Ab&cd1`, SQL*Plus prompts for `cd1` and consumes the next heredoc line.
The user is created with a different password than typed, or the connect fails. Step 5 accepts
such passwords, so only the later tools break. Fix: add `SET DEFINE OFF` as the first line of
each heredoc. The user-creating scripts should also reject `&`, and `"` where they do not yet.

### C2. `-v` (xtrace) prints SYS, observer and wallet passwords to the terminal
Root cause: `prompt_password` at `common/dg_functions.sh:825-829` calls `resume_verbose_trace`
*before* `echo "$password"`, so xtrace shows `+ echo <pw>`. Each caller's assignment
`X=$(prompt_password ...)` and each later use (`verify_sys_password "$pw"`,
`export SYS_PASSWORD="$pw"`) is traced as well. Affected callers:
- `dg_functions.sh:976,998,1000`
- `standby/05_clone_standby.sh:210-256, 426-430`
- `standby/07_verify_dataguard.sh:111`
- `primary/09_configure_fsfo.sh:330,364,377`
- `fsfo/observer.sh:250-318`
- `trigger/create_role_trigger_dedicated_user.sh:324`

`README.md:114` claims tracing is "suppressed around password prompts". **[repro]**
Fix: keep tracing paused through the `printf '%s\n' "$password"` inside `prompt_password`, and
wrap every caller's password block in `pause_verbose_trace`/`resume_verbose_trace`.

### C3. `-n/--check` is accepted and announced, then ignored
`enable_verbose_mode` logs "Check mode enabled. The script will stop before making changes."
(`common/dg_functions.sh:92-93`). However, `CHECK_ONLY` is never read by:
- `primary/01_gather_primary_info.sh` (still writes `primary_info_*.env` and copies orapw)
- `primary/02_generate_standby_config.sh` (still writes the `.env`, pfile, TNS and DGMGRL
  files; under `--regenerate` it rewrites the `.env`)
- all five `trigger/*.sh` (create or replace packages, triggers, users and services after one `y`)

Fix: honour `CHECK_ONLY` before the first write or mutation, or reject `-n` in these scripts.

### C4. Numbered scripts ignore `--help` and unknown flags
`enable_verbose_mode` only picks out known flags, and it is the only argument handling in:
- `primary/01_gather_primary_info.sh`, `04_prepare_primary_dg.sh`, `06_configure_broker.sh`,
  `09_configure_fsfo.sh`, `13_set_max_availability.sh`
- `standby/03_setup_standby_env.sh`, `07_verify_dataguard.sh`
- `trigger/create_role_trigger.sh`, `trigger/create_role_trigger_dedicated_user.sh`

`02` and `05` match only their documented flags (`05:35-47` silently ignores `--channel 4`).
`./primary/13_set_max_availability.sh --chek` or `-h` runs the real step. In addition,
`fsfo/observer.sh:762-790` requires the NFS mount and a config before it can print usage.
Fix: add a `-h|--help` case and a `-*) unknown option → usage, exit` case to the shared parser.

### C5. A missing option value causes a silent rc=1 that collides with documented exit codes
`dg_handoff.sh:144-161`, `dg_sync_impact.sh:119-126` and `get_dg_config_url.sh:71-76` read `$2`
and run `shift 2` under `set -e`. When the value is missing, `shift` fails and the script exits 1
with no message. For `dg_handoff.sh` that is "WARNING" (usage errors are documented as 3); for
`dg_sync_impact.sh` it is "fatal" (bad arguments are documented as 2). **[repro]**

The generated `_verify.sh` (`dg_handoff.sh:2130-2140`) has no `set -e`, so `-u` given as the last
argument loops forever. **[repro]**

Related: leading-zero values such as `08` pass the digit check and then fail in bash octal
arithmetic (`dg_sync_impact.sh:136-152`, `dg_handoff.sh:1074`).
Fix: `[[ $# -ge 2 ]] || usage_error "$1 requires a value"` before every `shift 2`, and normalise
values with `$((10#$v))`.

### C6. `TNS_ADMIN` is ignored when reading or editing Net configuration
The following hard-code `$ORACLE_HOME/network/admin`:
- `common/setup_dg_wallet.sh:499` (sqlnet.ora)
- `fsfo/observer.sh:415` (sqlnet.ora)
- `standby/03_setup_standby_env.sh:687,782` (listener.ora / tnsnames.ora)
- `primary/04_prepare_primary_dg.sh:92,163`
- `dg_handoff.sh:410-415` (reads `SQLNET.EXPIRE_TIME`)

`add_observer/` and `observer_sys_to_sysdg/` already use
`${TNS_ADMIN:-$ORACLE_HOME/network/admin}`. Shared or relocated `TNS_ADMIN` directories are common
on AIX. In that setup the scripts edit files Oracle never reads, and the failures surface later
as confusing tnsping, ORA-12154 or wallet errors. Fix: one helper, used everywhere.

### C7. Passwords on process argv (visible in `ps -ef`)
- `mkstore ... -createCredential "$alias" "$user" "$password"` appears in:
  - `common/setup_dg_wallet.sh:420` (SYS)
  - `fsfo/observer.sh:345,360`
  - `add_observer/02_setup_observer_host.sh:315`
  - `observer_sys_to_sysdg/02_switch_observer_credentials.sh:288`
- `add_observer/README.md:45` states passwords are "never accepted via argv". `setup_dg_wallet.sh`
  says mkstore has no stdin-based way to take the credential. When the secret argument is omitted,
  `-createCredential <alias> <user>` documents prompting for it; check on one 19c home whether
  that prompt reads a pipe.
- The generated `_verify.sh` takes `-u user/pass` and runs
  `sqlplus -s -L "$APP_USER/$APP_PASSWORD@$EZCONNECT"` (`dg_handoff.sh:2132-2135, 2200`). It
  should use `sqlplus -s -L /nolog` with `SET DEFINE OFF`, because the Easy Connect Plus string
  contains `&`, and send `CONNECT` on stdin.
- `export SYS_PASSWORD` (`dg_functions.sh:1000`) hands the SYS password to every child process.
  On AIX `ps eww` shows it. Remove the `export`.

### C8. Listener and tnsnames editing helpers are loose and only half-fixed
- `listener_has_global_dbname` (`common/dg_functions.sh:1109`) runs `index(line, "GLOBAL_DBNAME=" target)`.
  It matches prefixes, so `cdb1_stby` matches `cdb1_stby_DGMGRL`; it counts commented lines; and
  it is case-sensitive. As a result steps 3 and 4 skip the plain static entry that RMAN needs.
  **[repro]**
- `add_sid_to_listener` (`dg_functions.sh:1191-1243`) has these problems:
  - The `/SID_LIST_LISTENER/` match is unanchored, so a comment line containing that text starts
    the paren count early.
  - A one-line `SID_LIST_LISTENER=(...)` definition gives `insert_line=1`. Both cases splice the
    `SID_DESC` into the wrong place and still return 0. **[repro]**
  - The header claims a backup that the function does not take.
  - `mv` from `$TMPDIR` drops a symlink and the file mode.
- Step 3 appends the whole TNS entries file when only one alias is missing
  (`standby/03_setup_standby_env.sh:798-808`), which duplicates aliases. Step 4 already has the
  per-alias fix (`primary/04_prepare_primary_dg.sh:100-155`).
  `add_observer/02_setup_observer_host.sh:173-190` repeats the step 3 bug.
- Step 5's gate `lsnrctl status | grep -q "$STANDBY_DB_UNIQUE_NAME"` (`05_clone_standby.sh:134`)
  also matches `_DGMGRL` services, host names and paths. Grep for `Service "<name>" has` instead.

### C9. Broker output is classified differently in every tool
- **Warnings counted as errors.** These treat any `ORA-`/`DGM-` text as an error, so a
  member-level `Warning: ORA-16789` becomes ERROR and exit 1 or 2:
  - step 7 (`standby/07_verify_dataguard.sh:285-319`)
  - `dg_handoff.sh:254-268, 2318-2321`
  - `add_observer/_lib.sh:121-123` (`dgmgrl_failed`)
