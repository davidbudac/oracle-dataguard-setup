What Data Guard Changes for Your Application

Oracle Data Guard protects the database by maintaining a physical standby. Application teams need to plan for the behavioral changes below before go-live.

Commit Latency Under SYNC

When transport is SYNC or FASTSYNC in Maximum Availability, commits wait for standby acknowledgement according to the configured mode. This improves data-loss protection, but chatty transaction patterns can see higher commit latency than a single-instance primary.

  • Batch small commits where the application can do so safely.
  • Watch transaction latency during network maintenance windows.
  • Keep idempotent retry logic for recoverable connection failures.

FORCE LOGGING and NOLOGGING Jobs

Data Guard relies on redo. NOLOGGING operations can create unrecoverable gaps on the standby unless FORCE LOGGING is in effect for the database or the relevant object scope.

  • Review direct-path loads, index rebuilds, and ETL jobs that request NOLOGGING.
  • Coordinate any temporary FORCE LOGGING changes with the DBA team.
  • Validate standby recovery after large maintenance loads.

Sequence Gaps After Role Change

Sequence values are not a gap-free business counter. Cached sequence values on the old primary can be discarded during switchover or failover, so applications must tolerate gaps.

Use sequences for surrogate keys. Use a separate controlled process for legally gap-free document numbers.

Cold-Cache Brownout

After switchover or failover, the new primary may have a colder buffer cache and different session state. The database can be open, while application latency remains elevated until hot blocks and execution paths warm up.

  • Expect a short brownout after the role change.
  • Use pool ramp-up instead of reconnecting every application worker at once.
  • Keep synthetic checks focused on application transactions, not just listener reachability.

Read-Only Standby Semantics

A mounted standby cannot serve application sessions. A standby opened READ ONLY WITH APPLY can serve reporting reads with Active Data Guard, but it remains read-only.

Behavior Application impact
DML on standby Fails with ORA-16000; send writes to the primary service.
Apply lag Recent primary commits may not be visible immediately on standby.
Read-your-writes Not guaranteed when a request writes to primary and then reads from standby.

Connection Strings and Retry Guidance

Use the role-aware descriptor from the handoff report for application write traffic. It lists both hosts and relies on the Data Guard service trigger to run the service only on the current primary.

  • Use short connect and transport timeouts so down hosts do not stall request threads.
  • Enable pool validation on borrow or an equivalent lightweight connection check.
  • Enable TCP keepalive on client hosts and review server-side SQLNET.EXPIRE_TIME.
  • Treat TAF as SELECT-only replay; in-flight DML still needs application retry and reconciliation.

Reach Both Hosts Before Go-Live

The application tier must be able to reach both database hosts on the listener port before a planned or unplanned role change. Firewalls, routing, DNS, and security groups must all allow both paths.

  • Run tnsping or equivalent connection checks to both hosts.
  • Run nc -z <host> <port> or the platform equivalent from every app network zone.
  • Include both hosts in monitoring and operational runbooks.
